# Hosted missions and private family foundation

Missions 1–4 support hosted Java/Python, private family progress and email-only parent sign-in. See DEPLOYMENT.md for your own hosting configuration, PROGRESS.md for release receipts and VALIDATION.md for evidence boundaries.

## Student experience

The header provides Parent sign in, Student sign in, Curriculum & unlocks, and progress. Parents see a dashboard with each child's missions, next challenge, learning concepts and recent activity. Students have separate drafts for eight mission/language contexts and the latest twelve runs. Three confirmed challenges finish a mission and unlock the next playable mission; future lessons remain coming soon. Guests can practice Mission 1 in Python. Locked missions remain read-only previews. Physical completion and demonstrated understanding remain distinct.

Family multiplayer means independent attempts with shared family progress. It does not mean simultaneous control. Retries/help do not subtract points. There is no official competitive ranking in this release. Parents create up to six active student aliases, rotate codes or revoke access. Student codes use 192 bits of randomness and appear only during setup/code generation, masked with Copy and Show controls; no child email or password is needed. Parents use short-lived email codes. Public legacy parent-code sign-in and connection are retired; existing data is preserved. The retained-profile limit is 24 students, including revoked profiles. Revocation retains work.

Signed-in edits automatically save the current mission/language source and selected challenge. A revision conflict preserves both versions for comparison. Sign-out remains available during a conflict, keeping unsynced work under its original local profile. The example/history return copy and legacy notes stay on the device; note forms and manual save controls are removed.

After Run, an immutable source/challenge snapshot is recorded. Successful unfinished challenges automatically run through the authoritative server checker. Only its confirmed targets award progress; pending is distinct from complete. A checked-attempt receipt lets lost replies retry without another compute reservation. Existing successful challenges can be practiced again without an unnecessary new progress check. Run history preserves source, duration, final robot measurements and bounded printed output; restoring keeps a return copy and does not auto-run. See [FAMILY-EXPERIENCE.md](FAMILY-EXPERIENCE.md) for the current implementation and release state.

The operational allowance is 60 hosted Java runs/progress checks per family per UTC day, at most two simultaneous family runs and one per profile. A shared service gate also caps all families at two simultaneous hosted runs and 120 hosted runs per UTC day. Reservations include family, profile and attempt IDs, so two students submitting the same attempt ID still consume separate slots. Ordinary/check leases expire after 120 seconds; traced practice reserves its slot for 420 seconds to retain the slot through the normal startup/playback/cleanup envelope. Signup does not expand this budget. A denied service reservation releases its family lease, but conservatively retains the family daily attempt count. This is a service budget, not a score penalty. Anonymous browser Python is independent of it. Full classroom rosters, teacher assignments, ranking and new missions remain later work.

## Runtime and authority

Python practice uses the existing credential-free, separate-origin Pyodide worker. Hosted Java uses a fresh Vercel Sandbox per run. Progress checks use actual Java or CPython in that same boundary, with the fixed-step model and result calculation **outside** the VM in the application gateway. Student commands are validated and ordered; they cannot submit a result or rewrite the authoritative model. A stored checked attempt includes source hash, language, target, model/runner version and snapshot identity.

The bootstrap snapshot contains Ubuntu, OpenJDK 21.0.12.1, CPython and bubblewrap. It contains no student source, application credentials, accounts or model. It was prepared with package-download access, then frozen with networking denied. Each student VM explicitly uses `persistent:false`, one vCPU, 2 GiB provider memory and a 65-second lifetime for checks/ordinary execution (345 seconds for traced practice, including startup). Explicit cleanup is awaited; the provider deadline remains if the gateway disappears. Snapshot storage itself persists and is billed separately.

Inside the VM, bubblewrap creates mount/user/PID/network isolation, drops capabilities and runs as numeric UID/GID 10001. The root filesystem and runtime are read-only. `/work` and `/tmp` are memory-backed; the VM memory budget bounds aggregate writes. Files are capped at 64 MiB, open files at 128, processes/threads at 64. Java heap is 96 MiB, metaspace 64 MiB and direct memory 16 MiB; the total VM limit is **not** the local Docker 256 MiB limit. The supported kernel requires a read-only bind of `/proc`; privilege separation prevents learner access to the relay's environment. Tests probe network, localhost relay, sudo, runtime writes and environment leakage.

Source is bounded at 16,000 characters, output at 8 KiB, commands at 2,000; loading/compilation and execution retain separate 45/20-second limits. A timeout inside the student process also enforces 20 seconds. The trusted relay has an ephemeral per-run capability and never receives application credentials or the model. Its streaming response explicitly disables proxy buffering. Server-issued run controls are encrypted, expire after 90 seconds for ordinary runs or 420 seconds for traced practice, and are bound to family/profile/epoch. Replies and Stop work across stateless requests.

CPython progress checking supports the taught `robot` API and ordinary Python syntax, including top-level await. Pyodide-specific JavaScript/browser interop or browser-only packages are practice features, not supported progress-check dependencies. Arbitrary clocks, randomness or concurrency do not qualify as deterministic competition code. S06 must prove a competition contract separately.

## Private data and sessions

Private Vercel Blob stores family documents and hashed access-code lookups. There is no public upload endpoint or client Blob token. The SDK requests uncached, uncompressed private reads: compression can return a weak `W/` ETag that cannot satisfy conditional writes. Writes use the strong ETag with bounded retries/backoff. This preserves concurrent experiment, draft and cleanup updates and makes run reservations atomic across instances.

`iron-session` provides encrypted HttpOnly, SameSite=Strict sessions, secure `__Host-` cookies over HTTPS, with a seven-day lifetime. Every API request rechecks the active profile and revocation epoch. Changes require the exact app Origin and JSON. An explicit profile header prevents an older browser tab from writing to a different profile after another tab signs in. Family views share aliases and milestone summaries, not other students' source. All responses use no-store.

Progress-check cancellation is durable: a private cancellation record covers creation races, and the stored VM name permits explicit Stop from another request. A cancelled check cannot commit completion. A cancellation arriving after a committed result reports that it already finished. Stale reservations expire after 120 seconds; a new request does not assume a previous Function's memory still exists.

## Reproduce and validate

`npm ci`, `npm run check` and both Vercel packages remain the offline/local acceptance path. `test:family` and `test:family-ui` are included in check. The latter exercises the built account UI with a disposable in-memory CAS store and real isolated local CPython/Java checks. It does not establish cloud-provider or email delivery. The live hosted suites provision disposable parent sessions for runtime and authorization checks; these fixtures do not establish parent sign-in or email delivery. `tests/hosted/release.spec.ts` covers student → Java/Python → shared progress, and the opt-in `tests/hosted/progression-release.spec.ts` covers all twelve challenges and eight saved drafts. Actual inbox sign-in and weekly delivery are separate release checks. DEPLOYMENT.md describes these gates and the protected production-candidate API check. Docker/JDK setup for local Java remains JAVA.md; run `npm run setup:checks` for the test-only CPython image. Provider checks use project-scoped Vercel development OIDC and private **staging** storage, loaded from an ignored environment file by the caller:

- `npm run test:provider`: actual runtime, protocol, wrong programs, isolation, cancellation and deadline.
- `npm run test:storage-provider`: real strong-ETag and concurrent-write proof, with disposable records.
- `npm run test:hosted`: browser family/auth/drafts/history/progress plus real runtimes against `HOSTED_APP_ORIGIN` (default test app port 4373).

Set `SANDBOX_SNAPSHOT_ID` only to the tested project snapshot. Set server-only `SESSION_PASSWORD` (at least 32 random characters), `APP_ORIGIN`, and the private `BLOB_READ_WRITE_TOKEN`. Never forward these to the VM, client build, Python origin, screenshots or logs. `VITE_HOSTED=1` enables the family UI and API package. `VITE_RUNTIME_ORIGIN` selects the exact distinct runtime origin. `ROBOLAB_HOSTED=1` enables the hosted API in the local test server. `APP_DIST` / `RUNTIME_DIST` allow separate test artifacts without overwriting a running workshop.

The deployed app requires `scripts/package-function.mjs` output; a static upload alone cannot run Java or family services. The Node 24 function has a 360-second ceiling to cover bounded teaching playback plus startup/cleanup. It contains its bundle, immutable relay entrypoints, Robot.java and the practice-only JDI TraceMain.java. Scored checks retain the independent 45/20-second startup/execution limits. `scripts/check-vercel.mjs` checks the package. Inspect desktop/narrow screenshots and test actual HTTPS headers, routing, OIDC, streaming and cancellation on the protected deployment before public promotion. Live-provider tests do not prove those Vercel Function details or learners’ actual browsers.

## Deployment authorization and staging

Use your own explicitly authorized app/runtime projects, protected staging and separate production data. Keep deployment credentials and provider receipts private. Do not enable Git auto-deploy implicitly.

To recreate the runtime on an authorized account, link the intended application project with Vercel CLI, pull its development OIDC environment into an ignored file, then run `node --env-file=.env.development.local scripts/setup-hosted-sandbox.mjs work/sandbox-base.json`. This creates a billed trusted setup VM and persistent snapshot; it is deliberately excluded from CI. Set the resulting snapshot ID and rerun the provider acceptance suite before deploying. Runtime package versions in a newly created base can differ; the receipt and provider checks must reflect the new base.

Parents select **Parent sign in** in the header, enter their email, then enter the six-digit code sent to that address. A new parent explicitly chooses **Create family**, adds student nicknames and shares the private student login cards. A returning parent resumes the existing family; several owned families require a choice after email verification. Student cards are sent in one setup email, and first-sign-in notifications follow the parent's preference.

Existing verified recovery addresses use ordinary email sign-in. The public old-code/unfinished-setup connection flow is removed. Existing sessions, profile IDs, student codes, drafts, history and completion remain. Any unlinked code-only family needs a separately authorized support decision; the app cannot invent email ownership. See PARENT-EMAIL.md for the transition history and current contract.

Creation requires verified email proof, the exact app Origin and JSON. It cannot silently replace an active student or another parent session. CAS reservations allow ten new families per UTC day across the service; retrying the same existing setup is allowed at the limit. Temporary browser challenge state supports interrupted-response retries during the original lifetime. Preserve the session secret during ordinary releases. Reusable parent codes are not saved in persistent browser storage or returned by the public signup/recovery routes.

The operator-only `scripts/provision-family.mjs` tool produces a private legacy-family credential for controlled setup/testing. That credential no longer has a public parent-code sign-in or connection flow. Use only an explicitly authorized store and keep its mode-0600 receipt private. Hosted runtime tests may inject a session for their own disposable parent fixture, which is not authentication evidence. Inspect failed provisioning before retrying.

For protected HTTPS acceptance set `HOSTED_APP_ORIGIN` to the stable app origin and `HOSTED_BYPASS_FILE` to the private JSON file containing the `bypassSecret`. The test runner also needs the corresponding staging Blob token. Bypass headers are attached only to application requests, never the Python origin. Traces and automatic screenshots are off; explicit screenshots contain synthetic aliases and no codes.

## Parent email sign-in and legacy recovery

Parents use a fresh email code whenever they need to sign in. Students keep their own codes, and a parent can replace or revoke a student's code without deleting saved work. There is no general parent-email change screen. Old code-only signup, parent-code login and code-issuing recovery endpoints are retired; old recovery links show guidance and do not change authentication. Preserve historical opaque recovery epochs and existing sessions.

Server-only settings: RESEND_API_KEY (sending-only, scoped to the verified sending domain), RECOVERY_EMAIL_FROM, and RECOVERY_ORIGIN. Keep the key out of VITE variables, the static runtime project, fixtures and logs. The existing SESSION_PASSWORD keys private email indexes, challenge proofs and temporary encrypted mail payloads; preserve it across releases. No child email addresses are collected. Email indexes contain family IDs and are revalidated against the authoritative current parent address before granting access.

Authentication challenges expire ten minutes after the original request, allow at most five wrong attempts, and retain their original expiry when resent. Authentication sends are limited to five per address per day, twenty per source IP per day and a sixty-second cooldown for new requests to an address. Setup and first-sign-in messages share the unchanged sixty-per-day service ceiling with authentication, with separate category limits and reserved room for requested sign-in. See PLAN.md for the complete budget, retry and queue-retention contract. Existing sessions, student codes and anonymous Python remain usable during an email outage; there is no parent-code fallback.

For migration, APP_ORIGIN remains the original production address; APP_ALTERNATE_ORIGIN is exactly https://robolab.vibecodingdad.com. Both are built into the isolated runtime's frame/CSP. RECOVERY_ORIGIN uses the custom address. Host-only cookies and local drafts remain on their original host; the original address remains working, and students sign in with their existing code to load server-saved work at the new address. No wildcard or automatic cross-host credential transfer is used.

## Practice execution tracing (review candidate)

[EXECUTION-TRACING.md](EXECUTION-TRACING.md) defines native Python monitoring and Java JDI line events, speed, Pause and Step across all four released missions. Traced practice permits five minutes of playback including Pause, 20 cumulative seconds of interpreter work outside host-controlled replies and 10,000 source visits. Replies remain authenticated, ordered and bounded; no trace field can change the trusted model or award progress. Java’s debugger and debuggee stay inside the same isolated namespace; no debugger port is exposed. The launcher uses a 24 MiB heap/32 MiB metaspace and the traced debuggee 64/48 MiB, retaining the existing aggregate container/VM limits. Scored checks run the original source without JDI or teaching delays. Python tracing requires browser stack switching; unsupported browsers retain ordinary Run at 1×. This candidate needs actual hosted JDI/streaming/Stop qualification before release; local Docker evidence is not provider evidence.

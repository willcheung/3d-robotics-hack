# Hosted Mission 1 and private family foundation

Mission 1 supports hosted Java/Python, private family progress and optional parent recovery. See DEPLOYMENT.md for your own hosting configuration and VALIDATION.md for evidence boundaries.

## Student experience

The top navigation opens **Curriculum & unlocks** and **Family & progress**. The curriculum contains the existing 16 core outlines and four optional extensions. Only L01 is playable. Each student has a private access code, separate Python/Java drafts, a bounded experiment history, and three checked rescue milestones. Completing all three finishes Mission 1; unreleased lessons remain coming soon. Correct execution and demonstrated understanding remain distinct.

Family multiplayer means independent attempts with shared family progress. It does not mean simultaneous control. Retries/help do not subtract points. There is no official competitive ranking in this release. Parents create up to six active student aliases, rotate codes or revoke access. Student codes use 192 bits of randomness; parent codes derive from a random 192-bit setup credential and a server HMAC. Codes appear only during setup/code generation, masked with Copy and Show controls; no child email or password is needed. The retained-profile limit is 24 students, including revoked profiles. Revocation retains work.

Anonymous Python practice remains available. Java practice requires family authentication because it consumes hosted compute. **Save draft** syncs the current language to the student's profile. Each save has a revision; a conflict preserves the editor and offers a side-by-side comparison before choosing a version. **Check & save progress** runs the source again on the server, where a separate trusted model checks the selected rescue. Practice logs cannot award completion. The last 12 experiment source snapshots remain available to inspect/restore. A history restore saves both the current and destination-language drafts first and does not auto-run.

The operational allowance is 60 hosted Java runs/progress checks per family per UTC day, at most two simultaneous family runs and one per profile. A shared service gate also caps all families at two simultaneous hosted runs and 120 hosted runs per UTC day. Reservations include family, profile and attempt IDs, so two students submitting the same attempt ID still consume separate slots. Stale leases expire after 120 seconds; signup does not expand this budget. A denied service reservation releases its family lease, but conservatively retains the family daily attempt count. This is a service budget, not a score penalty. Anonymous browser Python is independent of it. Full classroom rosters, teacher assignments, ranking and new missions remain later work.

## Runtime and authority

Python practice uses the existing credential-free, separate-origin Pyodide worker. Hosted Java uses a fresh Vercel Sandbox per run. Progress checks use actual Java or CPython in that same boundary, with the fixed-step model and result calculation **outside** the VM in the application gateway. Student commands are validated and ordered; they cannot submit a result or rewrite the authoritative model. A stored checked attempt includes source hash, language, target, model/runner version and snapshot identity.

The bootstrap snapshot contains Ubuntu, OpenJDK 21.0.12.1, CPython and bubblewrap. It contains no student source, application credentials, accounts or model. It was prepared with package-download access, then frozen with networking denied. Each student VM explicitly uses `persistent:false`, one vCPU, 2 GiB provider memory and a 65-second lifetime. Explicit cleanup is awaited; the provider deadline remains if the gateway disappears. Snapshot storage itself persists and is billed separately.

Inside the VM, bubblewrap creates mount/user/PID/network isolation, drops capabilities and runs as numeric UID/GID 10001. The root filesystem and runtime are read-only. `/work` and `/tmp` are memory-backed; the VM memory budget bounds aggregate writes. Files are capped at 64 MiB, open files at 128, processes/threads at 64. Java heap is 96 MiB, metaspace 64 MiB and direct memory 16 MiB; the total VM limit is **not** the local Docker 256 MiB limit. The supported kernel requires a read-only bind of `/proc`; privilege separation prevents learner access to the relay's environment. Tests probe network, localhost relay, sudo, runtime writes and environment leakage.

Source is bounded at 16,000 characters, output at 8 KiB, commands at 2,000; loading/compilation and execution retain separate 45/20-second limits. A timeout inside the student process also enforces 20 seconds. The trusted relay has an ephemeral per-run capability and never receives application credentials or the model. Its streaming response explicitly disables proxy buffering. Server-issued run controls are encrypted, expire after 90 seconds, and are bound to family/profile/epoch. Replies and Stop work across stateless requests.

CPython progress checking supports the taught `robot` API and ordinary Python syntax, including top-level await. Pyodide-specific JavaScript/browser interop or browser-only packages are practice features, not supported progress-check dependencies. Arbitrary clocks, randomness or concurrency do not qualify as deterministic competition code. S06 must prove a competition contract separately.

## Private data and sessions

Private Vercel Blob stores family documents and hashed access-code lookups. There is no public upload endpoint or client Blob token. The SDK requests uncached, uncompressed private reads: compression can return a weak `W/` ETag that cannot satisfy conditional writes. Writes use the strong ETag with bounded retries/backoff. This preserves concurrent experiment, draft and cleanup updates and makes run reservations atomic across instances.

`iron-session` provides encrypted HttpOnly, SameSite=Strict sessions, secure `__Host-` cookies over HTTPS, with a seven-day lifetime. Every API request rechecks the active profile and revocation epoch. Changes require the exact app Origin and JSON. An explicit profile header prevents an older browser tab from writing to a different profile after another tab signs in. Family views share aliases and milestone summaries, not other students' source. All responses use no-store.

Progress-check cancellation is durable: a private cancellation record covers creation races, and the stored VM name permits explicit Stop from another request. A cancelled check cannot commit completion. A cancellation arriving after a committed result reports that it already finished. Stale reservations expire after 120 seconds; a new request does not assume a previous Function's memory still exists.

## Reproduce and validate

`npm ci`, `npm run check` and both Vercel packages remain the offline/local acceptance path. `test:family` and `test:family-ui` are included in check. The latter exercises the actual built account UI with a test-only in-memory CAS store and never claims provider/runtime proof. The same four setup browser tests also run in the live hosted suite. `tests/hosted/release.spec.ts` covers the full new-family → student → Java/Python → shared-progress journey; DEPLOYMENT.md describes the protected production-candidate API check. Docker/JDK setup for local Java remains JAVA.md. Provider checks use project-scoped Vercel development OIDC and private **staging** storage, loaded from an ignored environment file by the caller:

- `npm run test:provider`: actual runtime, protocol, wrong programs, isolation, cancellation and deadline.
- `npm run test:storage-provider`: real strong-ETag and concurrent-write proof, with disposable records.
- `npm run test:hosted`: browser family/auth/drafts/history/progress plus real runtimes against `HOSTED_APP_ORIGIN` (default test app port 4373).

Set `SANDBOX_SNAPSHOT_ID` only to the tested project snapshot. Set server-only `SESSION_PASSWORD` (at least 32 random characters), `APP_ORIGIN`, and the private `BLOB_READ_WRITE_TOKEN`. Never forward these to the VM, client build, Python origin, screenshots or logs. `VITE_HOSTED=1` enables the family UI and API package. `VITE_RUNTIME_ORIGIN` selects the exact distinct runtime origin. `ROBOLAB_HOSTED=1` enables the hosted API in the local test server. `APP_DIST` / `RUNTIME_DIST` allow separate test artifacts without overwriting a running workshop.

The deployed app requires `scripts/package-function.mjs` output; a static upload alone cannot run Java or family services. The Node 24 function has a 90-second ceiling and contains only its bundle, immutable relay entrypoints and Robot.java. `scripts/check-vercel.mjs` checks the package. Inspect desktop/narrow screenshots and test actual HTTPS headers, routing, OIDC, streaming and cancellation on the protected deployment before public promotion. Live-provider tests do not prove those Vercel Function details or learners’ actual browsers.

## Deployment authorization and staging

Use your own explicitly authorized app/runtime projects, protected staging and separate production data. Keep deployment credentials and provider receipts private. Do not enable Git auto-deploy implicitly.

To recreate the runtime on an authorized account, link the intended application project with Vercel CLI, pull its development OIDC environment into an ignored file, then run `node --env-file=.env.development.local scripts/setup-hosted-sandbox.mjs work/sandbox-base.json`. This creates a billed trusted setup VM and persistent snapshot; it is deliberately excluded from CI. Set the resulting snapshot ID and rerun the provider acceptance suite before deploying. Runtime package versions in a newly created base can differ; the receipt and provider checks must reflect the new base.

Parents now open **Family & progress → Create family**, enter a parent nickname, save the displayed parent code privately, then choose **I saved my code — add students**. Add each student's alias and copy their separate code. Each person returns through **Sign in**. A browser tab retains a temporary setup credential in sessionStorage until the parent acknowledges saving their code; reloading or retrying a lost response retrieves the same family and code. This temporary credential is private like an access code. Once acknowledged, it is removed. Optional verified parent email recovery is described below; enable it while the parent code is still available. Existing provisioned families keep working.

Creation requires the exact app Origin and JSON, permits anonymous setup or a retry by the same parent, and refuses switching an active account into a new family. CAS reservations allow ten new families per UTC day across the service; retrying an existing setup is allowed at the limit. Family and hashed-invite writes can recover after a partial failure. No plaintext access codes or raw setup keys are stored in private family documents. Rotating the session secret invalidates unfinished code retrieval, so preserve it during ordinary releases.

Operator-only bootstrap remains available when needed: load only the intended private store environment and run `node --env-file=<ignored-environment-file> scripts/provision-family.mjs <new-private-receipt.json>`. The receipt is created with mode 0600, refuses overwriting, and contains the parent access code. Share it privately; do not commit it. Students are created inside Family & progress. A failed provision needs inspection before retrying.

For protected HTTPS acceptance set `HOSTED_APP_ORIGIN` to the stable app origin and `HOSTED_BYPASS_FILE` to the private JSON file containing the `bypassSecret`. The test runner also needs the corresponding staging Blob token. Bypass headers are attached only to application requests, never the Python origin. Traces and automatic screenshots are off; explicit screenshots contain synthetic aliases and no codes.

## Parent email recovery

The parent can add/change a recovery email in Family & progress, using the current parent code and a 15-minute email verification link. Students never need email: sign in with their own code, Save draft to resume across devices, and Check & save progress for checked rescues. A parent can replace a lost student code without deleting saved work. Parent email recovery works only after verification; an old family without a verified email still needs its parent code.

Server-only settings: RESEND_API_KEY (sending-only, scoped to your verified sending domain), RECOVERY_EMAIL_FROM, and RECOVERY_ORIGIN. Keep the key out of VITE variables, the static runtime project, fixtures and logs. The existing SESSION_PASSWORD also keys private email indexes and retry credentials; preserve it across releases. No child email addresses are collected. Private parent email and token hashes stay in the family store; email indexes contain family IDs and are revalidated against the current verified address before use.

Email quotas use a durable private CAS document: 60 requests/day across the service, 5/address/day, 20/source-IP/day and 60 seconds between requests for an address. Unknown addresses count equally and receive the same public receipt. Global and per-address budgets intentionally also limit the initial small service; future scaling must review anti-abuse controls. Resend failure does not reveal whether an email has an account. Ask to retry after the cooldown; the current code remains valid until confirmed recovery.

Recovery links carry the token in the fragment, never a server query, and the app removes it from the address bar. Explicit POST confirmation avoids email scanners consuming access. A fresh random browser retry key binds a consumed link's retry receipt; losing both that key and the response requires a new recovery email. Replacement invalidates old parent sessions/codes, preserves students' epochs/data, and uses a distinct opaque epoch plus a profile-bound code hash so a failed competing invite write cannot become valid later, including with the previous epoch-only reader.

For migration, APP_ORIGIN remains the original production address; APP_ALTERNATE_ORIGIN is exactly https://robolab.vibecodingdad.com. Both are built into the isolated runtime's frame/CSP. RECOVERY_ORIGIN uses the custom address. Host-only cookies and local drafts remain on their original host; the original address remains working, and students sign in with their existing code to load server-saved work at the new address. No wildcard or automatic cross-host credential transfer is used.
